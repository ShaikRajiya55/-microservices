In our chip design pipeline, Register-Transfer Level (RTL) port contracts across hardware modules like PicoRV32 are specified across multiple decoupled sources: base Verilog source releases extracted from /app/data/picorv32-v1.0.tar.gz containing picorv32.v, physical synthesis DB records stored in SQLite at /app/data/design_db.sqlite under the rtl_ports table, and real-time Engineering Change Order (ECO) overrides stored in Redis at localhost:6379 under keys formatted as eco:port:<module_name>:<port_name>. Your goal is to build a production Python FastAPI application at /app/main.py and an executable launcher at /app/run_service.sh listening on 0.0.0.0:8000 that reconciles port specifications across all three data sources according to strict source precedence and parameter math resolution.

When resolving a module port contract, your reconciliation engine must prioritize active Redis ECO records (REDIS_ECO) above all others, followed by active SQL database rows (SQL_DB), falling back to base Verilog module declarations (VERILOG). If a Redis ECO record contains a JSON string with a status of DELETED or a SQL row has is_active set to 0, that port must be excluded from the canonical contract unless a higher priority active override exists. For Verilog source parsing, extract module parameter defaults declared in parameter blocks #(parameter NAME = VALUE), evaluate mathematical expressions within port ranges such as [ADDR_WIDTH-1:0] or [DATA_WIDTH-1:0] into numeric bounds, identify port directions (input, output, or inout), and default scalar wire ranges to 0 for both MSB and LSB.

Your FastAPI service must implement five REST endpoints. The health endpoint at GET /health must return an HTTP 200 JSON object with status ok and boolean connectivity flags for redis, sql, and verilog_archive. The module listing endpoint at GET /modules must return a JSON object with a modules array containing all unique module names sorted in strict ascending ASCII order. The contract endpoint at GET /modules/{name}/contract returns the reconciled contract containing module_name, port_count, checksum, and a ports list sorted strictly in ascending ASCII order by port name. Each port item must report name, direction, msb, lsb, width calculated as abs(msb - lsb) + 1, and winning source. If a requested module does not exist or has zero active ports, return HTTP 404 with detail string Module '<name>' not found.

The contract checksum field must be a lowercase 64-character SHA-256 hex digest computed over canonical formatted strings <name>:<direction>:<msb>:<lsb>:<source>\n for each port in sorted order. Finally, your application must support live ECO management via POST /modules/{name}/eco, accepting a JSON payload with port_name, direction, msb, lsb, and status to write to Redis returning {"status": "applied", "key": "..."}, as well as DELETE /modules/{name}/eco/{port_name} which writes {"status": "DELETED"} to Redis returning {"status": "deleted", "key": "..."}.
